# tomatodev (development)

Global tool, environment, and worktree/branch rules live in `~/.claude/CLAUDE.md`.
Ownership boundaries, verification, and DOM/data rules are identical to tomatofarm; this file adds the isolation and release deltas.

## Origin and promotion

- This is the development environment and the default place to start feature work. tomatofarm is production.
- Promotion is user-gated and carries app code only. This checkout never pushes or deploys tomatofarm.
- The isolation overlay stays here and is never promoted: the `tomatodev` Firebase app name and shared-backend guards, fail-closed FCM (`tomatodev-fcm-disabled`), the dev APK and retained native config, build metadata, and the `tomatodev-` cache-version prefix. See [docs/reference/ENVIRONMENT_BOUNDARIES.md](docs/reference/ENVIRONMENT_BOUNDARIES.md).
- Do not add a second git remote; the repository boundary check allows only `origin`.

## Work unit

- The current user request is the source of truth. Do not resume work from historical plan, review, evidence, or next-action files.
- Implement directly by default. Write a plan only for materially ambiguous work or several independent modules.

## Ownership boundaries

- Code ownership is in `ARCHITECTURE.md`; CSS/UI ownership is in `docs/DESIGN_SYSTEM.md`.
- Root source files are authoritative. `www/` is generated by `scripts/copy-www.js` and never edited directly.
- Edit CSS only in `styles/`, `admin/admin-hig.css`, or `test-mode-v2.css`. Root `style.css` is generated by `scripts/generate-style-entry.mjs`.
- Runtime assets are declared in `runtime-assets.js`. If a cached source or asset changes, regenerate derived files and bump `sw.js` `CACHE_VERSION` in the same change.
- UI and feature modules use the `data.js` facade. Private `users/{owner}/...` paths must use the shared owner resolver/repository and fail closed when owner selection is unresolved; never create a second writable alias.
- Preserve existing persisted fields through domain serializers and round-trip tests. Treat `setDoc` without merge as a full overwrite.
- One interactive DOM root has one controller that owns its rendering and internal actions. Patch values in place during input gestures; rerender only for structural changes. Do not depend on an ancestor handler that an inner `stopPropagation()` can block.
- For life-zone art or NPC work, read `docs/LIFE_ZONE_ASSETS.md` before editing.

## Verification

- Run the most relevant behavioral tests first, then the applicable suite. Buttons, inputs, modals, persistence, and update flows require behavior tests.
- Exercise every user-facing UI change in a browser with `node scripts/dev-start.mjs`, then stop the server. Never use `python -m http.server` for local verification.
- Every completed handoff includes a clickable Markdown link to the delivered artifact: a verified public HTTPS URL for mobile/external downloads (APK, archive, report, image), absolute repository-file links for code-only work. Never provide an unlinked path.

## Release

- A clear implementation request authorizes implementation, checks, browser verification, task commit, safe integration, and one TomatoDev Pages release unless the user says local-only or no-deploy.
- Shared surfaces such as `app.js`, `data.js`, navigation, modal infrastructure, runtime assets, CSS, or `sw.js` require a grouped release and combined regression check.
- Immediately before integration and push, fetch `origin`, verify the exact commit/file delta, and rebuild the integration if `origin/main` moved.
- Only a clean canonical `main` may run `npm.cmd run check:repository` and `git push origin main`. Push once; never force-push.
- Push only to `aretenald2018-sys/tomatodev` and deploy only `https://aretenald2018-sys.github.io/tomatodev/`. Never push or deploy tomatofarm from here.
- Do not deploy Firebase, Functions, or Android/Wear packages from TomatoDev until dedicated development project and application IDs exist.
- After Pages deployment, verify the expected commit and exercise the changed development flow.
